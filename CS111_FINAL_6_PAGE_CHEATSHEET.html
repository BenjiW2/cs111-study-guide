Process / Thread Core

  • Process: running program + address space + resources + kernel bookkeeping.
  • Thread: execution stream inside a process. Own PC, registers, stack, state; shares process address space/files.
  • PCB/TCB: kernel records for process/thread: state, registers, scheduling info, address-space info, open files.
  • Kernel: privileged OS core. System call: controlled user -> kernel entry.
  • Context switch: save current thread state, restore next thread state.
  • Thread states: running, ready, blocked. Ready means runnable but not on CPU.

fork

fork() duplicates the calling process. Both continue after the call.

Wherereturn valuemeaning
child0I am the newly created child.
parentchild PIDI created this child.
error-1No child created.
  • Memory is separate after fork; variables are copied, not shared.
  • Open file descriptors are inherited.
  • Output order is not guaranteed unless synchronized or waited.
  • Loop with N unconditional forks: total processes 2^N, new processes 2^N - 1.
pid_t pid = fork();
if (pid == 0) { /* child */ }
else { /* parent; pid is child's PID */ }

execvp

execvp loads a new executable file into the current process. Same PID, new program image.

char *args[] = {"wc", "-l", NULL};
execvp(args[0], args);
perror("execvp"); exit(1);
  • p means search PATH, like shell. "wc" might resolve to /usr/bin/wc.
  • Replaces old code, globals, heap, stack. Does not create a new process.
  • If successful, never returns to old code.
  • argv array must end with NULL.
  • File descriptors usually survive across exec unless close-on-exec.

waitpid / Zombies

int status;
waitpid(pid, &status, 0);
if (WIFEXITED(status))
  WEXITSTATUS(status);
  • waitpid(pid,NULL,0): wait for exact child, ignore status, blocking wait.
  • Collects child's exit status and prevents zombie persistence.
  • status is encoded; use WIFEXITED, WEXITSTATUS.

Shell Pattern

pid_t pid = fork();
if (pid == 0) {
  dup2(fd, STDIN_FILENO);
  close(fd);
  execvp(args[0], args);
  perror("execvp"); exit(1);
}
waitpid(pid, NULL, 0);

Parent keeps shell/program alive. Child redirects FDs, then becomes command.

File Descriptors

fdnameconstant
0stdinSTDIN_FILENO

2stderrSTDERR_FILENO
  • open returns lowest available fd.
  • read(fd,buf,n), write(fd,buf,n), close(fd).
  • dup2(oldfd,newfd): make newfd refer to same open file description as oldfd. Direction matters.

Pipes

int fds[2]; pipe(fds);
// fds[0] read end, fds[1] write end
  • Data written to fds[1] is read from fds[0].
  • After fork, both processes inherit both ends.
  • EOF only when all write ends are closed. Exam trap: leaked write end -> reader blocks forever.
  • Pipe command pattern: child1 stdout -> pipe write; child2 stdin -> pipe read; close unused ends in all processes.

C/C++ Syntax Traps

  • p->field means (*p).field.
  • &x address of x. *p object pointed to by p.
  • Array of strings: char *argv[] = {"ls","-l",NULL};, array of char pointers; each string ends in '\0'; argv list ends in NULL.
  • std::deque<T> is a double-ended queue, not the verb dequeue. push_back add at back, front first, pop_front remove first.

Race / Critical Section

  • Race condition: correctness depends on timing/interleaving.
  • Critical section: shared-state access that must be mutually exclusive.
  • Atomicity: operation appears indivisible to other threads.
  • Thread-safe: correct under concurrent calls.
  • Interrupts alone do not solve multicore races: another core can still run.
// x++ is read, add, write; not atomic
int tmp = x; tmp = tmp + 1; x = tmp;

Mutex / RAII

std::mutex m;
void f() {
  std::unique_lock<std::mutex> lock(m);
  // critical section
} // auto unlock
  • Creating unique_lock/lock_guard locks the mutex.
  • Leaving scope unlocks automatically.
  • Use unique_lock with condition variables because wait must unlock/relock.
  • Manual m.lock(); ... m.unlock(); is error-prone, especially early returns.

Condition Variables

std::unique_lock<std::mutex> lock(m);
while (!predicate) {
  cv.wait(lock);
}
// predicate true while lock held
  • wait(lock) atomically releases mutex and sleeps; on wake, reacquires before returning.
  • Always use while, not if: spurious wakeups, stale predicates, wrong waiter woken.
  • Change shared state while holding lock, then notify.
  • notify_one: one waiter can proceed. notify_all: multiple/different predicates or simplicity.

Monitor Pattern

Monitor = mutex + shared state + condition variables + methods that hold lock while checking/updating state.

class Buffer {
 mutex m; condition_variable nonempty, nonfull;
 queue<Item> q; int cap;
 void put(Item x) {
  unique_lock<mutex> lock(m);
  while (q.size()==cap) nonfull.wait(lock);
  q.push(x); nonempty.notify_one();
 }
 Item get() {
  unique_lock<mutex> lock(m);
  while (q.empty()) nonempty.wait(lock);
  Item x=q.front(); q.pop();
  nonfull.notify_one(); return x;
 }
};

Selected-Thread Grouping

If prompt says exactly selected threads proceed, counters alone are unsafe. Store waiter records.

struct Waiter { bool assigned=false; condition_variable cv; };
deque<Waiter*> H, O;
void try_group() {
 if (H.size()>=2 && O.size()>=1) {
  Waiter *h1=H.front(); H.pop_front();
  Waiter *h2=H.front(); H.pop_front();
  Waiter *o=O.front(); O.pop_front();
  h1->assigned=h2->assigned=o->assigned=true;
  h1->cv.notify_one(); h2->cv.notify_one(); o->cv.notify_one();
 }
}
void hydrogen() {
 Waiter self; unique_lock<mutex> lock(m);
 H.push_back(&self); try_group();
 while (!self.assigned) self.cv.wait(lock);
 lock.unlock(); bond();
}
  • h1->cv = (*h1).cv. Wake exact selected waiter.
  • &self address of this thread's local waiter record.

Deadlock

Coffman conditions: mutual exclusion, hold-and-wait, no preemption, circular wait.

  • Prevent circular wait by global lock ordering.
  • Acquire all resources at once, or release before waiting.
  • Starvation != deadlock. Starvation: one waits too long though system progresses. Deadlock: cycle, no progress.
// order rule
lock(A); lock(B); ... unlock(B); unlock(A);

Low-Level Lock Implementation

  • Single core: disabling interrupts can protect lock/scheduler internals briefly.
  • User mutex does not disable interrupts for your entire critical section.
  • Multicore: disabling interrupts on one core is insufficient; need atomic instructions.
  • Test-and-set/swap/CAS allow read-modify-write atomicity.
  • Busy waiting wastes CPU but can be necessary inside low-level spinlocks, especially very short waits.

Common Sync Bugs

  • Wait predicate checked with if instead of while.
  • Notify before changing state.
  • Holding lock during slow/external work.
  • Sleeping after partially consuming resources.
  • Forgetting "in progress" state: boarding/crossing/merging but not finished.
  • Using notify_all when exactly one specific waiter must proceed, without assignment state.

Dispatching vs Scheduling

  • Scheduler: policy deciding which ready thread should run.
  • Dispatcher: mechanism that switches CPU to chosen thread.
  • Dispatcher is OS code, not a special high-priority thread.
  • Preemption does not release locks; only owning thread can safely release.

Dispatcher/scheduler share ready-queue state; scheduler updates policy/data, dispatcher quickly selects/runs.

Events Causing Dispatch

  • Running thread blocks on I/O/condition/page fault.
  • Thread exits.
  • Timer interrupt/time slice expires.
  • Higher-priority thread becomes ready.
  • Yield/system call may trigger scheduling.

Priority Queues

Implementation: one ready queue per priority level. Dispatcher picks highest non-empty priority queue; ties often round-robin.

4.4 BSD Scheduler

  • Real Unix scheduler example. Combines priority, recent CPU usage, user hints, interactivity heuristics.
  • Dispatcher records start/stop times; scheduler estimates recent CPU usage.
  • Rule: least recent CPU usage -> higher priority; lots recent CPU -> lower priority.
  • Interactive/I/O-bound: run briefly then block -> low recent CPU -> high priority.
  • CPU-bound: uses full slices -> accumulates CPU -> lower priority.
  • CPU-bound should not starve forever: while waiting, recent CPU stops increasing/decays, priority rises.
  • Overloaded/tied case can devolve to round robin among highest-priority runnable threads.

Unix nice

  • nice=0 default.
  • +19: very nice, emphasize CPU usage, lower priority.
  • -20: least nice, de-emphasize CPU usage, higher priority.
  • nice is a hint/input, not absolute CPU control.
nice -n 19 ./background_script.sh
nice -n -20 ./urgent

Multicore Scheduling

  • Shared: ready queues/scheduler data + lock.
  • Per core: interrupts, dispatcher, currently running thread.
  • Run k highest-priority ready threads on k cores.
  • New high-priority ready thread may preempt lowest-priority running thread.
  • Need synchronization around scheduler queues because multiple cores access them.
  • Work-conserving: do not leave core idle when ready work could run.
  • Work stealing: idle core takes work from busier core/queue. Helps load balance.
  • Core affinity/locality: running same thread on same core may preserve cache/TLB warmth.

Exam Phrases

  • Reducing recent CPU usage, by blocking/sleeping/yielding, can improve BSD effective priority.
  • Recent CPU usage, not lifetime CPU usage.
  • Preemption can expose interleavings but does not itself make code safe.
  • Voluntary yield not required for preemptive scheduler to regain CPU; timer interrupt can do it.

CS111 Final Cheatsheet: Linking, Memory, Virtual Memory, Paging

Program Memory Layout

  • Text/code: instructions, often read-only/shareable.
  • Data: initialized globals/statics.
  • BSS: zero-initialized globals/statics.
  • Heap: dynamic allocation, arbitrary lifetimes.
  • Stack: calls, locals, return addresses; per thread.

Linking / Loading

  • Compiler -> object files with machine code + symbols + relocation info.
  • Linker combines object files, resolves symbols, creates executable.
  • Static linking copies library code into executable.
  • Dynamic linking uses shared libraries loaded/connected at load/run time.
  • Relocation entry: "fix this address later."
  • Import table entry: "this external symbol/library function is needed."
  • Debug info maps machine code back to source names/lines/types.

Allocator / Heap

  • malloc returns heap block; free releases it.
  • Leak: lost pointer to allocated live block; memory cannot be reused.
  • Dangling pointer: pointer to freed/invalid object.
  • Double free: freeing same block twice corrupts allocator state.
  • Internal fragmentation: waste inside allocated block.
  • External fragmentation: free memory split into unusable holes.
  • First fit: first adequate hole. Best fit: smallest adequate hole. Coalescing merges adjacent free blocks.

Virtual Memory

Each process sees its own virtual address space. MMU translates virtual -> physical and checks permissions.

  • Goals: isolation/protection, relocation, sharing, sparse address spaces, demand paging.
  • Virtual address generated by CPU/program. Physical address indexes RAM.
  • Invalid/protected access -> trap/page fault/segfault.

Base and Bound

If VA < bound, PA = base + VA; else trap.
  • Supports relocation/protection for one contiguous segment.
  • External fragmentation issue.
  • Message-passing style: kernel can translate/copy between process address spaces using each process's base/bound.

Segmentation

Multiple variable-sized regions, each with base, bound, permissions: code, heap, stack, etc.

  • Address = segment number + offset.
  • Check offset against segment bound; add segment base.
  • Allows different permissions/sharing per segment but still external fragmentation.

Paging

Fixed-size virtual pages map to fixed-size physical frames.

VA = VPN + offset. Page size = 2^k -> offset is low k bits. PA = PPN + same offset.
  • Page table maps VPN -> PPN + valid/protection/dirty/reference bits.
  • No external fragmentation for physical memory; possible internal fragmentation in last page.
  • Page table can be huge; use multi-level page tables, TLB.

TLB

  • Hardware cache of recent translations.
  • TLB hit: fast translation. Miss: consult page table.
  • Context switch may require TLB flush or address-space identifiers.

Demand Paging

  • Pages loaded into RAM only when used.
  • Page fault: page not resident or permission problem. Kernel handles fault.
  • On nonresident valid page: choose frame, maybe evict victim, read needed page from disk, update table, restart instruction.
  • Dirty victim must be written back before reuse; clean victim can be discarded.

Replacement

policyidea/trap
Randomsimple baseline
FIFOevict oldest resident; can evict hot pages; Belady anomaly possible
LRUevict least recently used; good but costly to implement exactly
Clockapprox LRU using reference bit; sweep clears reference bits, evicts unreferenced page
  • Local/per-process replacement: victim from faulting process.
  • Global replacement: victim from any process; can improve utilization but interference.

Thrashing

System spends most time paging, little time executing. Symptoms: paging disk near 100%, CPU idle/low useful work. Fix by reducing working set, adding memory, or improving paging I/O; scheduling alone usually does not fix.

Disk Basics

  • Magnetic disk cost: seek time + rotational latency + transfer time.
  • Sequential access much faster than random access.
  • Disk scheduling tries to reduce movement and improve throughput.
  • Locality matters: place related metadata/data near each other.

Disk Scheduling

Filesystem Goals

  • Map names -> files -> disk blocks.
  • Persistence, performance, sharing, protection, crash consistency.
  • Tradeoffs: metadata overhead, fragmentation, sequential/random access, growth, locality.

Unix V6 / BSD Inodes

Inode stores metadata and block pointers. Directory maps name -> inode number.

  • Metadata: type, owner, permissions, size, timestamps, link count, block pointers.
  • Direct pointers: point directly to data blocks.
  • Single-indirect: pointer to block full of data-block pointers.
  • Double-indirect: pointer to block of pointers to indirect blocks.
Block index = file offset / block size. Offset in block = file offset % block size.

For pointer-count problems: pointers per indirect block = block size / pointer size.

Directories / Links

  • Directory is a file containing mappings from names to inode numbers.
  • Path lookup walks components one directory at a time.
  • Hard link: another directory entry for same inode; link count tracks names.
  • Symbolic link: special file whose contents are another pathname; lookup substitutes target path.
  • Deleting name removes directory entry; inode/data freed when link count zero and no opens.

Free Space

  • Free list: linked list of free blocks; simple but can have locality/recovery issues.
  • Bitmap: one bit per block; easy to find contiguous runs; compact for large disks.
  • Allocation policy affects locality and fragmentation.

Block Cache

  • Cache disk blocks in memory to avoid repeated I/O.
  • Delayed write/write-back improves performance but risks data loss/inconsistency on crash.
  • Synchronous write safer but slower.
  • Dirty block = cache differs from disk and must be written eventually.

Fragmentation

  • Internal fragmentation: allocated unit larger than data, unused space inside unit.
  • External fragmentation: enough free space exists but split into pieces.
  • BSD FS uses block/fragments ideas to balance large-block throughput and small-file waste.

Flash Memory

  • Cannot overwrite like RAM/disk sector. Must erase before rewrite.
  • Erase is block/granularity larger than page writes.
  • Blocks wear out after finite erase cycles.
  • FTL maps logical block addresses to physical flash locations.
  • Wear leveling spreads erases across device.
  • Garbage collection compacts live pages and erases blocks.
  • Write amplification: internal writes > user writes.

Crash Recovery Problem

Filesystem updates often require multiple disk writes. Crash between writes can leave metadata inconsistent.

  • Data loss: recent user data missing but filesystem structure ok.
  • Inconsistency: metadata contradicts itself; worse.
  • Atomic operation: appears all-or-nothing.
  • Durability: once reported done, survives crash.
  • Consistency: filesystem invariants hold.

Common Inconsistencies

  • Inode points to block marked free.
  • Block allocated to two files.
  • Directory entry points to missing/free inode.
  • Link count does not match directory references.
  • Free bitmap/list disagrees with inodes.
  • Cached dirty metadata lost while data written, or vice versa.

fsck

  • Post-crash checker scans filesystem and repairs inconsistencies.
  • Can be slow; needs whole-structure scan.
  • May preserve consistency but not necessarily recover newest intended data.
  • Repairs should be idempotent: safe to repeat after another crash.

Ordered Writes

Write blocks in a safe order so every crash point leaves recoverable/acceptable state.

  • Example allocation: initialize data/inode before making directory entry visible.
  • Can trade data loss for metadata consistency.
  • Hard to get right for complex multi-block updates.

Write-Ahead Logging

  1. Write intended updates to log.
  2. Commit log transaction.
  3. Apply updates to real filesystem locations.
  4. Checkpoint/truncate log when safe.
  • Recovery: committed transaction replayed; uncommitted ignored.
  • Write-ahead rule: log reaches disk before home-location updates.
  • Transaction groups updates into all-or-nothing unit.

Virtual Machines

  • VM virtualizes whole hardware-like machine, not just process address space.
  • Guest OS runs inside VM; hypervisor/VMM manages real hardware.
  • Benefits: isolation, consolidation, portability, snapshots.
  • Challenges: privileged instructions, device virtualization, memory virtualization, performance.

Trust / Ethics

  • Trust = accepting vulnerability to another actor/system because you expect acceptable behavior.
  • Agency: who can act/decide? Who is affected?
  • Trust by assumption: assume system/person is trustworthy.
  • Trust by inference: infer from evidence/history/signals.
  • Trust by substitution: trust intermediary/certifier/tool instead.
  • Over-trust: relying beyond warranted evidence/capability.
  • Discuss stakeholders, pervasiveness, time/long-term effects, incentives, accountability.

Final-Code Traps

  • After fork, both parent and child continue from next instruction.
  • execvp success means no old-code lines after it run.
  • FD redirection before exec survives into new program.
  • Pipe EOF requires all write ends closed.
  • waitpid waits for process, not thread.
  • Threads share globals/heap/open files; processes after fork do not share ordinary memory.
  • User-level thread metadata lives in process memory, so fork copies it as data.
  • Condition variable waits must be in while.
  • Interrupt disabling is internal/brief; user mutex does not disable interrupts for whole critical section.

Address Translation Checklist

  1. Identify page/segment size.
  2. Split virtual address into VPN/offset or segment/offset.
  3. Check valid/protection/bound.
  4. Map VPN->PPN or add base.
  5. Keep same offset.
  6. If invalid/not resident: page fault/trap.

Inode Offset Checklist

  1. logical_block = offset / block_size.
  2. inside = offset % block_size.
  3. If logical block in direct range, use direct pointer.
  4. Else subtract direct count; check single indirect capacity.
  5. Else subtract single capacity; compute double-indirect indexes.
  6. Pointers per indirect block = block size / pointer size.

One-Line Exam Answers

  • Race? Shared mutable state accessed without sufficient synchronization.
  • Deadlock? Cycle of waiting with no preemption/order violation.
  • Thrashing? Working sets exceed memory, paging dominates.
  • BSD priority? Recent CPU use lowers priority; waiting/blocking improves it.
  • Dynamic linking? Shared library symbols resolved/loaded at load/run time.
  • Crash consistency? Need ordered writes/logging/fsck to preserve metadata invariants.
